# ParFlow 数据共享平台维护与优化文档 v1.0

## 1. 运维责任

|角色|责任|当前需落实|
|---|---|---|
|业务负责人|下载规则、审批标准、公告、维护窗口|指定负责人及替补|
|科学数据负责人|源文件、变量字典、网格/投影、许可、版本和科学验收|正式字典及首发版本签字|
|审核管理员|按标准审核并写意见，处理用户问题|响应时限、撤销条件|
|技术维护人员|部署、故障、备份、权限、监控、升级|服务器和交接联系人|
|安全/信息管理负责人|账号、个人信息保留、公开许可和安全审查|制度待确认|

用户名、邮箱、申请姓名/单位/目的属于业务敏感资料；不能把生产 SQL、.env 或原始日志随意放进公开工单。面向项目负责人的需求书不应包含任何实际密码。

## 2. 维护对象与边界

1. 网页和 API；2. MySQL；3. worker 与子进程；4. 原始科学数据/转换器/版本清单；5. 有效 ZIP 和工作目录；6. 公告说明；7. 邮件、底图、证书等外部服务。
维护模式只暂停新增申请/任务，不自动停止已开始的所有传输或任务，也不是完全只读数据库开关。

## 3. 日常巡检建议

|频率|项目|方法和判断|
|---|---|---|
|每天/值班开始|网站/API|/api/health 返回 status=ok、database=mysql；再实际打开地图页|
|每天|worker|查看进程、任务日志和排队年龄；没有任务时“最后任务心跳旧”不一定表示 worker 离线|
|每天|任务积压/失败|比较排队数、最老任务年龄和错误码；关注 WORKER_LOST、CLIP_FAILED、空间/超时错误|
|每天|磁盘|原始数据、任务输出、ZIP、日志分别统计，不仅看 ZIP 目录|
|每天|备份|检查备份任务成功、大小合理、摘要和可读性；不能只看文件名存在|
|每周|抽样功能|登录、编号搜索、我的申请/下载、管理员说明修改；试运行账号与真实用户分开|
|每周|外部服务|标准/地形底图、SMTP 实际收信、域名/证书到期|
|每月|恢复演练|在隔离库/目录恢复，核实名额/权限/目录及代表性下载|
|每季度或重大变更后|容量/权限|最大流域压测、并发、异常路径、停机恢复、管理员名单|
|每次数据发布|科学校验|源摘要、投影、网格方向、有效掩膜、PFB 数值、PFSOL、包完整性|

频率是建议，不是已实现自动化。根据试运行规模可调整。

## 4. 只读检查示例

### 4.1 服务检查

```bash
bash scripts/run-linux.sh check
ss -ltnp 'sport = :8000'
ps -u "$USER" -o pid,args | rg '[p]ython.*(app.py|datahub.workers.queue)'
```

仓库未提供可直接安装的 systemd 单元；进程托管由部署方配置。不要用 worker --once 做健康检查。

### 4.2 数据库诊断（只读）

```sql
SELECT status,COUNT(*) AS jobs FROM download_jobs GROUP BY status;
SELECT MIN(created_at) AS oldest_queued FROM download_jobs WHERE status='queued';
SELECT error_code,COUNT(*) AS failures
FROM download_jobs WHERE status='failed'
GROUP BY error_code ORDER BY failures DESC;
SELECT state,COUNT(*) AS archives,SUM(byte_size) AS bytes
FROM result_archives GROUP BY state;
SELECT state,COUNT(*) AS slots FROM small_basin_slots GROUP BY state;
SELECT status,COUNT(*) AS applications FROM large_basin_applications GROUP BY status;
SELECT COUNT(*) AS users FROM users;
SELECT COUNT(*) AS basins FROM watersheds;
SELECT version_code,status,published_at FROM dataset_versions ORDER BY id DESC;
```

排查明细需要账号权限；向外提交问题时使用脱敏的任务 ID、错误码和时间，不附全表用户信息。

## 5. 备份策略

### 5.1 必须备份

|对象|恢复价值|建议策略|
|---|---|---|
|MySQL 业务库|账号、已用名额、申请/审核、版本、任务、内容|定期一致性备份；重要变更前额外备份|
|原始 PFB/边界/模板|无法仅凭业务库重建|源版本冻结后至少另存一份，校验 SHA256|
|科学代码、转换器、冻结清单|证明结果可复现|按发布版本整体保存|
|配置/证书/凭据|恢复服务连接|加密保密备份，限管理员访问|
|有效 ZIP 与引用工作目录|业务下载连续性|按需求保留；若不备份须明确恢复后重生成策略|
|审计与日志|问题追溯|按批准期限独立归档|
|前端/后端发布产物、依赖清单|回滚|保留上一可用版本及关联数据库变更说明|

仅复制 .venv 不是可靠的跨系统部署备份；应保存可复现依赖、安装记录与目标系统信息。

### 5.2 MySQL 导出模板

使用具有备份所需权限的专用账号。以下为手工执行模板，路径与账号均需由维护人员替换；密码交互输入，不写进命令行。备份目录先创建，使用带时间戳的新文件名，不覆盖唯一备份。

```powershell
mysqldump --host=127.0.0.1 --user=concn_backup --password --single-transaction --quick --hex-blob --no-tablespaces --set-gtid-purged=OFF --default-character-set=utf8mb4 --result-file="D:\CONCN-backup\concn_datahub_YYYYMMDD_HHMM.sql" concn_datahub
```

命令中的 concn_backup 为专用备份账号示例，执行前需创建并授予必要权限。不要把测试库作为正式库导出。导出不使用 --databases，以便恢复到另一个明确选择的新库。导出时避免结构变更，并确认命令退出码成功。

Windows 使用 --result-file 可避免某些 PowerShell 版本重定向编码的问题；--single-transaction 用于 InnoDB 一致性导出。具体语义及权限见 [MySQL 官方备份文档](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)。

业务库和有效结果需要联合恢复时，先开启维护模式、等待/安排停止写任务与文件传输，再做协调快照；MySQL 单事务导出不保证文件系统在同一时刻一致。

### 5.3 恢复演练

1. 明确目标是全新的隔离恢复库 concn_restore_日期，不是线上 concn_datahub。
2. 核查备份文件来源、时间、摘要和可读性，准备对应源数据/代码/转换器快照。
3. DBA 新建隔离库及独立恢复账号，确认 SQL 内没有指向生产库的 USE/CREATE DATABASE 语句。
4. 登录 MySQL 客户端，明确使用隔离库，再通过 SOURCE 读取文件：
```sql
USE concn_restore_YYYYMMDD;
SOURCE D:/CONCN-backup/concn_datahub_YYYYMMDD_HHMM.sql;
```
以上占位库必须事先建立；命令只示意，不自动创建和不覆盖生产。
5. 核查 22 张表、关键行数、外键、用户已用名额、申请审批状态、版本摘要及内容。
6. 对照结果文件；若备份不含有效 ZIP，先拟定状态修复和重新生成方案，不能让数据库继续错误宣称文件可用。
7. 隔离运行网站进行权限和代表性科学验证，禁止复用生产 SMTP 发真实邮件，禁止连接生产任务目录。
8. 记录实际恢复时间、失败项、修复项和可达的 RPO/RTO，再由负责人确认是否切换。

**建议讨论目标：**每日备份意味着最差可能丢失约一天业务变更，并非自动达成零丢失。RPO（允许丢失多久数据）与 RTO（允许停机多久）须结合成本签字，未验证前不承诺数值。

## 6. 文件清理

已实现的 worker maintain：
- 回收租约失效的任务状态；
- 识别过期结果；
- 在没有有效下载会话/传输租约时删除指定结果 ZIP；
- 更新结果/任务状态；
- 按规则释放无活跃引用且未激活的预留名额。

**未完整实现：**自动清理裁切中间文件、失败任务目录、长期日志、过期认证令牌、审计归档。当前工作目录为诊断保留，因此“ZIP 已过期”不等于磁盘空间全部回收。

拟增加清理工具时必须：
1. 默认先生成候选清单和预计释放空间，提供 dry-run；
2. 只允许在解析后的 CONCN_JOB_ROOT 内操作，拒绝根目录、源数据目录、符号链接越界；
3. 联查任务状态、执行尝试、结果状态和传输租约；
4. 跳过在途任务、有效结果引用和无法确认的目录；
5. 删除前保留必要诊断日志并记录审计；
6. 单批数量/时间限制，失败可重试但不误删；
7. 使用测试目录演练后启用。不要用“删除 jobs 整个目录”的方式释放空间。

账号已激活名额、审批、数据版本不是临时缓存；不能随意清表重置。

## 7. 数据版本发布与维护

- 同一发布版本的源文件、裁切代码、转换器、网格参数和摘要必须一致。
- 新数据放入新版本目录，不覆盖在用文件名。
- 先校验 14 位编码唯一、七级父子关系、投影、模板与 PFB 尺寸、掩膜非空。
- 核对单位、空值、层数、字段含义、引用、许可、适用范围，记录数据负责人。
- 用目标平台生成代表性与极端流域，验证 PFB 原始值、方向、窗口、域几何及 SHA256。
- 经确认冻结新的清单，登记版本及流域可用性，再向用户开放。
- 切换新版本时保留历史申请的版本边界，不把旧审批自动赋予新版本。
- 下架会使新下载检查拒绝已下架版本；历史记录仍应保留。
- 当前 worker 不再比较工具代码和转换器摘要；原始数据摘要检查保留，工具变化仍需科学输出验证。
- 当前 publish-local 是本地验证工具，生产通用发布工具、跨版本执行环境并存与图形化数据上传仍待实现。

## 8. 使用说明与公告维护

管理员后台 → 双语内容 → 新增或编辑。帮助类型显示在使用说明，公告类型显示在公告；保存 published 公开，draft 不公开。正文纯文本保留换行，不支持 Markdown 渲染、图片上传或自动翻译。

常规更新流程：准备双语内容 → 数据/业务负责人复核 → 管理员保存 → 中文/英文各刷新检查 → 记录修改目的。
发布条款和科学引用需同时核对数据版本的冻结 license/citation；改帮助文章不会改变已经签署/提交的条款快照。当前无内容历史还原功能，重要修改前导出或保存原文到版本化文档。

## 9. 故障分级与处理

建议分级（响应时间待项目负责人确认）：
- P0：越权泄露、源数据损坏、大范围无法下载且无绕行。
- P1：网站/数据库/worker 停止、队列持续积压、批量裁切失败。
- P2：单流域或单用户失败、底图或邮件不可用、页面显示问题。
- P3：文案、体验和优化建议。

处理顺序：记录时间与错误码 → 评估影响面 → 必要时维护模式 → 保留日志和样本 → 定位最小原因 → 修复并测试 → 恢复 → 复盘。先保存证据再清理，不能靠反复重启掩盖同一问题。

|症状|优先检查|恢复动作|
|---|---|---|
|网站打不开|进程、端口、IP、防火墙|恢复正确服务和访问地址|
|我的申请空白|旧前端 randomUUID、脚本加载失败、登录状态|部署新构建并刷新；检查 API 和控制台|
|下载 randomUUID 报错|局域网 HTTP 缺 secure-context API|当前已改 getRandomValues 兼容生成，不降低浏览器安全设置|
|我的下载闪烁|旧版全表 loading 的定时刷新|当前改静默更新；无在途任务停止|
|排队长期不动|worker、数据库、同用户在途任务|恢复 worker，核查旧任务租约，勿重复启动大量 worker|
|WORKER_LOST|强停、崩溃、磁盘/网络|排查资源并让维护收敛，必要时按权限重试|
|CLIP_FAILED|任务日志、路径、源摘要、转换器|修复根因；不对已发布摘要随意打补丁|
|授权/文件 410|审批、结果、下载会话到期|重新申请或获取结果|
|容量不足|中间文件、ZIP、源副本和日志|先有依据清理终态临时文件或扩容|
|同网访问失败|子网/客户端隔离/旧防火墙 IP|更新规则或更换允许互访的网络|
|登录被限流|账户锁定、代理真实 IP|等锁定恢复；生产完善可信代理与集中限流|
|地图背景慢|外部图层或密钥|检查网络及提供方，保持流域数据可用性判断独立|

### 10.1 性能测试建议

先定义样本：最小流域、中位流域、最大流域、狭长/多部分/边界贴网格流域；每种选多个而不是只一个编号。记录机器、数据版本、层数和尺寸、并发数、首屏/接口 P50/P95、裁切时长、峰值 RSS、磁盘读写、输出大小、失败率。

建议逐步从 1 个 worker、1 个任务开始，增加并发直到瓶颈清楚。当前 lock_context 会锁平台单例及用户，部分路径可能串行化；不能仅增加 worker 就承诺线性提速。内存估计不是硬限制，容器/cgroup 等资源限制需目标平台实测。

可能的优化：
- 用经校验且不可变的数据版本缓存哈希验证结果，明确失效规则，不能直接跳过科学完整性检查。
- 地图按视窗/级别按需加载、矢量切片和几何简化，需保证下载使用原始科学边界。
- 大文件传输可评估受控内部重定向或对象存储签名链接；必须维持账号/审批到期与撤销语义，不能直接公开 ZIP URL。
- 数据库连接池、查询计划和索引按实测优化，避免为了页面统计反复扫描全表。
- 将全局配置锁缩短/细分需配额、审批和并发回归验证，不能破坏两个名额约束。

## 11. 更新和回滚

UI 修改：构建和浏览器检查；API/权限修改：相关集成测试；科学代码或源数据修改：新版本和科学回归；数据库修改：增量脚本、备份及恢复副本验证。

每次上线记录：发布编号、变更文件、数据库迁移号、配置差异（不含秘密）、测试结果、回滚点、负责人、时间。
遇到失败先判断数据兼容性，旧代码能否读取新结构；不兼容时不能直接切回。数据版本回滚与程序回滚分别处理，历史任务快照必须还能解释。

禁止：重跑 bootstrap 覆盖线上、清空业务库来解决报错、把测试库恢复覆盖生产、在任务运行时覆盖原始科学文件、关闭认证以解决下载问题。

## 12. 安全与合规待办

- 生产 HTTPS 和 Secure Cookie；管理员密码及凭据独立保密管理。
- 生产应用 DML 账号与 DBA/备份账号分离；不公开 3306、私有目录。
- 定期核对管理员和禁用账号；验证码、实名、MFA 等当前未实现，按风险另定。
- 数据提供方许可、地图提供方署名、用户数据使用告知需审核。
- 注册/邮件/申请的滥用防护和多账号规避当前仅有基础措施，不能承诺“一人两流域”技术核验。
- 明确账号注销、历史审批/审计保留期限与个人信息响应流程，目前产品化流程未完成。
- 不将运维健康信息暴露为包含路径、密码或用户明细的公开接口。

## 13. 维护日志模板

|项目|填写内容|
|---|---|
|事件/变更编号|例如 OPS-日期-序号|
|开始与结束时间|含时区|
|操作人/批准人|姓名或岗位|
|影响范围|页面、用户、任务、数据版本|
