# 数据库继承与部署交接

## 1. 交付哪些内容

| 内容 | 位置及交付方式 |
| --- | --- |
| 当前源码 | 审查当前工作区修改及新增文件后提交指定版本，通过 GitHub 交付 |
| 当前业务数据库 | 用 mysqldump 导出 concn_datahub，通过受控私下传输交付 |
| 原始 PFB | /path/to/data/inputs，单独传输或授权共享存储 |
| 边界与模板 | /path/to/data/PFBAS，保留 shp 配套文件和 geotiff |
| 历史下载结果 | backend/jobs，完整保留相对目录；若 CONCN_JOB_ROOT 改过，以配置实际目录为准 |
| 配置和工具 | 按 .env.example 重新配置数据库账号、科学路径、地图密钥、邮件和 Linux pfmask-to-pfsol |

MySQL 物理文件位置由服务端 datadir 配置决定；项目 database 目录只含 SQL 结构脚本。不要在数据库运行时直接复制物理文件作为普通迁移备份。应导出交接时的业务快照，不以旧备份代替。

SQL 可以继承用户、密码哈希、目录、规则、申请审核、内容和任务历史，但不包含科学源文件与下载 ZIP。迁移应按双方确定的范围保留账号和相关业务记录；不要在未核对关联关系时自行过滤用户。MySQL 自身的 concn_app 连接账号不在业务库备份内，目标服务器需新建。

## 2. GitHub 与私下交付分开

GitHub 可保存源码、配置模板、SQL 迁移、依赖清单及使用文档。不要上传真实 .env、SQL 数据备份、.local、密码文件、有效结果 ZIP、数据库物理文件或科学源数据。私有仓库也不替代数据库备份渠道。

具体服务器的路径清单和测试记录不属于公共源码文档，应单独保管。现有 .gitignore 不会自动排除所有新命名的 .sql；database/migrations 中的结构 SQL 应保留，业务备份应放在被忽略的 .local 中。添加文件前检查 git status，提交前检查暂存差异。仅克隆已有旧提交可能缺少当前尚未提交的代码和新增文件。

## 3. 固定源码、数据库与文件的交接时间

可先做在线演练备份；正式切换时先停止新业务写入，等待现有裁切和下载完成，通过应用正常取消不应继续的排队任务。再停止本项目 web 和空闲 worker，保持 MySQL 运行，导出数据库并复制 jobs。不要在导出期间改表或运行数据库迁移。若源站继续接收新写入，目标库就不再是最终最新副本，需要约定再次同步和最终切换时间。

停机前在业务库检查（只读）：

```sql
SELECT status, COUNT(*) AS total FROM download_jobs GROUP BY status;
SELECT COUNT(*) AS active_transfers FROM download_sessions
WHERE transfer_lease_until > UTC_TIMESTAMP(6);
```

running、packaging、cancel_requested 应处理完毕后再切换；排队任务的保留/取消需双方明确。不要手工仅改状态绕过名额、outbox 和授权清理。复制本身不延长结果过期时间；worker 启动后仍会按过期策略处理。

## 4. 在源服务器导出

使用有备份权限的 MySQL 账号；示例 root 是 MySQL 管理员，不是 Linux root。密码通过 -p 交互输入，不写在命令中。使用与源数据库兼容的 mysqldump。以下命令只在确认要导出时执行：

```bash
cd /path/to/ParFlow-CONCN-Share-Platform
umask 077
handoff_dir="$PWD/.local/handoff-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$handoff_dir"
mysqldump --no-defaults \
  --host=127.0.0.1 --port=3306 \
  -u root -p --single-transaction --quick --no-tablespaces \
  --set-gtid-purged=OFF --hex-blob --default-character-set=utf8mb4 \
  --result-file="$handoff_dir/concn_datahub.sql" concn_datahub
```

检查该命令退出码为 0 且没有错误；失败时生成的半截 SQL 不能用于交付。`--single-transaction` 为当前 InnoDB 表提供一致读；它不能保证磁盘 jobs 与数据库同步，文件一致性由前面的停写流程保证。未使用 --databases，备份不负责创建库，便于明确恢复目标。--hex-blob 保留二进制哈希值，--no-tablespaces 避免导出服务器表空间定义。

导出成功后，在同一终端计算传输校验值：

```bash
(cd "$handoff_dir" && sha256sum concn_datahub.sql > SHA256SUMS)
```

通过 SSH/SFTP 等方式私下传输 SQL、校验文件和必要的 jobs、科学数据；为交接副本限制读取权限，校验和只能确认传输完整，不能替代隔离恢复验证。不导出 concn_datahub_test 的合成账号和测试记录。另行记录交付源码 commit、时间和数据文件清单。

## 5. 目标服务器恢复

先安装并启动目标 MySQL，优先匹配当前 MySQL 8.4 系列，确认支持 utf8mb4_0900_ai_ci。所有命令中的安装位置、socket 和账号按目标机器实际调整。恢复到全新空库；若对方已有业务库，先备份并使用隔离实例演练，不在有数据的库上直接导入。

在目标机器 MySQL 管理会话中创建空库：

```sql
CREATE DATABASE concn_datahub CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

先在收到文件的目录执行 `sha256sum -c SHA256SUMS`。校验通过后用目标 mysql 客户端导入，下面假定该终端当前目录包含 SQL：

```bash
mysql --no-defaults --host=127.0.0.1 --port=3306 -u root -p concn_datahub < concn_datahub.sql
```

目标若只允许 socket 管理登录，将 host/port 换成目标的 --socket 参数。导入应完整成功，不使用 --force 跳过 SQL 错误。不要在恢复库上执行 bootstrap 或重新灌入默认 seeds，避免覆盖继承的配置与账号。

恢复后为网站新建连接账号，示例仅适用于目标尚不存在该用户的情况，密码占位符必须替换为新生成的强密码：

```sql
CREATE USER 'concn_app'@'localhost' IDENTIFIED BY 'REPLACE_WITH_NEW_RANDOM_PASSWORD';
GRANT SELECT, INSERT, UPDATE, DELETE ON concn_datahub.* TO 'concn_app'@'localhost';
```

不要把管理员/root 密码配置为网站运行密码。若采用远程数据库，账号 host、网络权限及连接配置需按实际目标调整。测试库另行创建并执行 001–004 迁移及默认 seeds，只给测试库相应测试权限；未准备测试库前不要执行集成测试。

## 6. 登录和临时令牌

用户和 password_hash 随业务库恢复，通常可使用原网站密码。建议双方在交接时确认：只在目标恢复副本上撤销旧会话、邮件操作令牌和临时下载授权，让用户重新登录。以下操作不是导入的必选步骤；选择采用后，在目标站开放访问之前运行：

```sql
START TRANSACTION;
UPDATE auth_sessions SET revoked_at=UTC_TIMESTAMP(6) WHERE revoked_at IS NULL;
UPDATE email_actions SET revoked_at=UTC_TIMESTAMP(6) WHERE revoked_at IS NULL;
UPDATE download_sessions SET status='revoked', transfer_lease_until=NULL WHERE status='active';
COMMIT;
```

这不删除账号、密码、申请或历史统计；原邮件链接和临时下载链接会失效。不能在尚有源站用户正常使用时误对源库执行。

## 7. 配置、数据与启动

安装 environment.yaml 和 backend/requirements/worker.txt，安装符合 frontend/package.json 要求的 Node，执行 npm ci/build。根据模板创建目标 backend/.env，并配置新 MYSQL_*、CONCN_HOST、CONCN_PORT、CONCN_PUBLIC_URL、CONCN_JOB_ROOT、三类科学输入路径及 PARFLOW_PFMASK_CMD。前端地图密钥按目标域名授权配置，重新构建。不要照搬本机绝对路径。

科学输入应与继承版本摘要一致；工具代码和转换器历史摘要不再拦截，但新 Linux 转换器的实际输出仍需验证。保持 jobs 内部的任务ID/attempt-次数目录和数据库 storage_key 对应。只改 job 根目录配置即可，不应批量改数据库内部相对路径。数据缺失或过期的旧 ZIP 不会因数据库导入自动恢复。

先启动 MySQL、网站并检查页面、权限和目录，核实继承任务与文件后再启动 worker。新旧站不要误连同一个业务库。旧站在新站验收前保留回滚副本，最终切换期间保持写入入口唯一，避免两边独立产生无法直接合并的新业务。

## 8. 验收与回滚

- 对照源快照和目标的各表行数，确认管理员/普通用户、版本、流域、申请和任务都继承。
- 原账号能登录，角色权限正确，目录搜索和内容页面正确。
- 有效历史 ZIP 的 storage_key、大小、SHA256 和磁盘文件一致；未交付/已过期文件如实列明。
- 在授权范围内提交真实小流域任务，确认队列、裁切、打包和浏览器下载完整通过。
- 目标域名/IP、地图、邮件和目标用户网络访问分别验证，不以健康接口代替全部验收。
- 失败时停止目标写入，保留错误日志和副本；恢复原站访问前先处理目标期间的新记录，不能静默丢失用户操作。
